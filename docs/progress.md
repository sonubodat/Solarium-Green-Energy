- **Full `docs/testing.md` verification pass completed** (§§3–11: Public, Auth, Vendor, Sales, Admin, pagination, Supabase-equivalent integrity checks via Prisma, end-to-end acceptance scenarios, and a real-browser frontend walkthrough of all four portals). Six real defects were found and fixed, each reproduced live before and after the fix, not assumed:
  1. **`VendorRegistration` had no unique constraint** on `login_identifier` — duplicate pending registrations could be created silently (the route's own `P2002` handling was dead code). Fixed with migration `20260825093500_vendor_registration_login_identifier_unique`; verified duplicate registration now returns `409`.
  2. **`Retry-After` header always said `60`**, even on the 15-minute auth/password-reset limiters, because a generic response helper overwrote the correctly-computed value. Fixed in `rate-limit.js`; verified the header now reports the real remaining window (~897s on a fresh trip).
  3. **`POST /admin/qr/:qrId/reassign` leaked the vendor's `passwordHash`** in the JSON response — every other vendor-returning endpoint wrapped with `publicVendor()`, this one didn't. Fixed; verified the field is gone from the response.
  4. **Deactivating a Vendor or staff user did not revoke their existing session** — a deactivated account kept full API access on its pre-existing session cookie (fresh logins correctly failed, but `requireAuth` never re-checked account status on existing sessions). This defeated the actual purpose of deactivation as an access-revocation control. Fixed in `middleware/auth.js`: `requireAuth` now rejects with `401` if the session's account is not `ACTIVE`. Verified live: a deactivated Vendor's existing session immediately returns `401`.
  5. **The public enquiry form broke whenever the optional Email field was left blank** — the frontend sent `email: ""` rather than omitting the key, and the backend's `.email().optional()` validator rejects an empty string. This broke the primary customer-facing conversion flow for the common case of a customer skipping an optional field. Fixed in `App.js`'s `submitLead` (strips empty `email`/`location` before sending, matching the existing pattern used for optional fields elsewhere); verified live in the browser.
  6. **The app's runtime connected via Supabase's transaction-mode pooler (port 6543)**, which is a documented Prisma incompatibility for interactive `$transaction()` under concurrent load — affecting every mutation in the app (not just leads). Reproduced live (intermittent `P2028` failures under load), root-caused with isolated port-comparison tests, and fixed by routing the runtime connection through `DIRECT_URL` (session-mode, port 5432) instead, matching what `prisma.config.ts` already used for the CLI. Verified with a 20-concurrent-transaction stress test (20/20 succeeded post-fix) and a clean browser walkthrough. See `architecture.md` for the scaling note this leaves for later.

Pinned all five to their currently-installed versions (`^17.4.2`, `^5.2.1`, `^8.3.0`, `^8.23.0`, `^4.4.3` respectively), matching the caret-range convention already used for `qrcode` and the exact-pin convention Prisma already uses for its own documented reasons. `frontend/package.json` was already properly pinned. Verified: `npm install` succeeds, lockfile reflects the new ranges, and the server boots and passes a live health check unchanged.
- **Fixed a real Render deploy-blocking bug**, found from an actual failed deploy log: `backend/prisma.config.ts` used `@prisma/config`'s `env()` helper for `DATABASE_URL`, which throws synchronously the instant the config module loads if the variable is unset — before Prisma even knows which subcommand is running. This meant `prisma generate` (triggered by the `postinstall` hook on every `npm install`) failed on Render with `PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL`, even though `generate` itself never needs database connectivity — it only reads `schema.prisma`. Fixed by using a plain `process.env.DATABASE_URL` lookup instead (verified via `@prisma/config`'s own source: `env()` is `if (!process.env[name]) throw`, a plain synchronous function, not special build-time analysis). Verified locally: `prisma generate` and `prisma migrate status` both still succeed unchanged against the real Supabase database. This fixes the *build*; it does not remove the requirement that Render's own environment variables actually include `DIRECT_URL` (preferred) or `DATABASE_URL` for the deployed app to connect to the database at runtime — confirm that's set in the Render service's Environment tab.
