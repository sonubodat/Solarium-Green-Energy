- **Fixed a real cross-site session cookie bug, found from the actual deployed frontend/backend**: after CORS was corrected to allow the deployed Vercel origin, staff login on the live Render backend returned `200` and appeared to work, but every subsequent Admin/Sales/Vendor request returned `401`. Live-diagnosed by inspecting the actual `Set-Cookie` header from the production login endpoint: `SameSite=Lax` with no `Secure` flag. Since the frontend (`*.vercel.app`) and backend (`*.onrender.com`) are different sites, a `SameSite=Lax` cookie is set successfully on login but is never attached to the following cross-site `fetch`/XHR requests — only `SameSite=None; Secure` cookies are sent cross-site. This meant `NODE_ENV` was not actually set to `production` in Render's environment (the code only switched to `SameSite=None; Secure` in that case). Two parts to the fix:
  1. **You need to set `NODE_ENV=production` (and/or `SESSION_COOKIE_SAME_SITE=None`) as an actual environment variable in Render's Environment tab for this service** — this is on you to do, not something in the repo.
  2. **Code hardening applied regardless**: `backend/src/services/auth.js`'s cookie functions previously derived `Secure` from `NODE_ENV === 'production'` alone, independently of `SESSION_COOKIE_SAME_SITE`. Since browsers reject a `SameSite=None` cookie outright if it lacks `Secure`, these two settings must never be able to drift apart. Added `cookieIsSecure()`, which forces `Secure` whenever `SameSite=None` is in effect *regardless* of `NODE_ENV` — so setting only `SESSION_COOKIE_SAME_SITE=None` (without also getting `NODE_ENV` right) can no longer produce a cookie the browser silently drops. Verified with three live cookie inspections: local dev (unchanged: `SameSite=Lax`, no `Secure`), `SESSION_COOKIE_SAME_SITE=None` forced via inline env with `NODE_ENV` still unset (now correctly `SameSite=None; Secure` together), and the actual production login endpoint (confirmed the pre-fix `SameSite=Lax`/no-`Secure` state directly, via a real request to `https://solarium-green-energy.onrender.com`).

  - Threaded a `forceRefresh` parameter through `AdminPage.js`'s `loadAdminResource(nextResource, page, statusOverride, assignmentOverride, forceRefresh)` and wired all 7 explicit "Refresh" buttons (Dashboard, Vendors, QR, Leads, Scans, Payouts, Audit Logs) to pass `forceRefresh: true`, so a user clicking Refresh always gets a real fresh read regardless of the cache window. Ordinary navigation between tabs still benefits from the cache (e.g. quickly switching back to a tab visited a few seconds ago).
  - `SalesPage.js` and `VendorPage.jsx` have no explicit Refresh buttons (confirmed via grep) — left untouched; their normal loads benefit from the cache automatically, and any GET immediately following a mutation (onboarding, QR assignment, vendor creation) already gets a cold cache thanks to the clear-on-mutation rule, so no special-casing was needed there.

Documented in `frontend/.env.example`: `REACT_APP_API_BASE_URL` must be **left unset** for this Vercel+Render setup — setting it to the direct `onrender.com` URL bypasses the rewrite and reintroduces the exact third-party-cookie problem being fixed here.
